# Contributing

Thanks for helping keep this library sharp.

## Reporting bugs

Open a [bug report](.github/ISSUE_TEMPLATE/bug_report.yml). Please include the skill or tool name, a minimal reproduction, the library version or commit, and the exact output you saw. For security issues, follow [SECURITY.md](SECURITY.md) instead.

## Proposing a change

For changes to an existing skill, reference, workflow, or tool, open a [feature request](.github/ISSUE_TEMPLATE/feature_request.yml). For brand-new skills, use the [skill proposal](.github/ISSUE_TEMPLATE/skill_proposal.yml) template.

New skills are added sparingly. The bar is:

- a real, recurring decision that isn't already covered
- groundable in official documentation (Google Search docs, Agent Skills spec) rather than opinion
- distinct enough from existing skills that the trigger phrasing in `description:` won't collide

If you're unsure whether a change should be a refinement to an existing skill or a new one, open the proposal anyway and we'll work it out in review.

## Authoring rules

- Keep each skill focused on one reusable decision or workflow.
- Put only essential instructions in `SKILL.md`; move supporting doctrine into reference files.
- Reference bundled resources with paths relative to the skill root, such as `references/example.md` or `assets/example.schema.json`.
- Edit the canonical shared files in `references/` and `schemas/`. The copies inside individual skills are generated by `bun run sync:skills` from those canonical sources.
- Prefer official sources when changing doctrine, and update `docs/source-map.md` when the source set changes materially.
- Write descriptions that begin with what the skill does and continue with "Use when..." trigger phrasings; this is how routing layers pick the right skill.

## Local checks

```bash
bun run sync:skills
bun run validate:skills
bun run smoke:install
bun run check:public
bun run build:cowork
```

`sync:skills` refreshes the self-contained bundles inside each skill. Commit those generated resource copies with the source changes that require them. Before requesting review, run `check:public` so the library is exercised through both its local validators and the external install surface (`skills-ref` and the real `skills` CLI). `build:cowork` is rarely needed locally — the release workflow runs it on `v*` tag pushes — but produces `dist/skills/*.zip` if you want to test Cowork upload manually.

## Review process

- Open a PR using the [pull request template](.github/PULL_REQUEST_TEMPLATE.md).
- CI runs `bun run check:public`; PRs need a green build before review.
- Doctrine changes need a linked official source. Tooling changes don't.
- Add a `[Unreleased]` entry in `CHANGELOG.md` for anything user-visible.
- Maintainers aim for a first response within five business days. Larger reshapes (new skills, reference reorganizations) take longer because they need a doctrine-coherence pass.

## Releases

The library carries one version that covers all skills. We tag `vX.Y.Z` on `main`, move `[Unreleased]` to a numbered section in `CHANGELOG.md`, and bump `package.json`. Consumers pin to a commit via `skills add`, so release tags are a coordination point; distribution happens via the commit hash.
